# Quark 2.0.0 — Deck Mode and Parity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship Quark 2.0.0 with an integrated gamepad/Steam Deck mode, then restore the missing 1.8.8 features and release artifacts.

**Architecture:** A native `gilrs` input thread emits Tauri events; a DOM focus layer in `deck.js` turns them into navigation, while `body.deck` CSS reshapes the existing screens. Parity work reuses the existing Rust core and adds missing Tauri commands plus UI branches; no second application and no new frontend framework.

**Tech Stack:** Rust 2021, Tauri 2, WebKitGTK 4.1, vanilla HTML/CSS/JS, `gilrs` 0.11 for Linux gamepads, Xvfb for screenshots.

**Spec:** `docs/superpowers/specs/2026-11-21-2.0-deck-mode-design.md`

## Global Constraints

- Linux only; Tauri 2; WebKitGTK 4.1; core `src/lib.rs` stays egui-free.
- Work only on `release/2.0.0`; never modify, merge, or push `main`.
- Window stays opaque: `transparent: false`, no outer border radius.
- Five UI languages and thirteen themes remain; every new label is added to all five JS catalogues.
- Deck input is ignored when `document.hasFocus()` is false or a game is running in the foreground.
- No full re-render per gamepad event; only focus state changes.
- One new native dependency: `gilrs = "0.11"`.

## Review Focus

- A gamepad held in one direction must not flood renders or skip two cards.
- A controller disconnecting/reconnecting must leave the UI usable, not stuck on a dead focus ring.
- Starting more than three store downloads must refuse clearly, not queue silently.
- Cancelling a download must stop the child process and leave the game in a non-installed state.
- The Deck layout must keep every action reachable without a mouse and without clipping at 1280×800.

### Task 2: Deck mode state, activation and fullscreen

**Files:**

**Interfaces:**
- Consumes: `deck_status`, `quark://gamepad`.
- Produces:
  - command `win_set_fullscreen(active: bool) -> Result<(), String>`
  - `window.QuarkDeck` with `enable()`, `disable()`, `toggle()`, `handle(action)`, `refocus()`.
  - config key `deck_mode`: `"auto" | "on" | "off"`.
  - `body.deck` class.

- [ ] **Step 1: Add fullscreen command and demo flag**

Register `win_set_fullscreen` in `main.rs`, using `window.set_fullscreen(active)`. Accept `--deck` as a demo arg and expose `deck: bool` in `Bootstrap`.

- [ ] **Step 2: Add the deck rail and translations**

Add a Réglages → Apparence card labelled `Mode Deck / manette` with options `Auto`, `Toujours`, `Désactivé`. Add all five translations.

- [ ] **Step 3: Implement `deck.js`**

On boot, call `deck_status`; enable if `deck_mode === "on"`, or `auto` and `steam_deck || gamescope`; also enable when a gamepad event first arrives in `auto`. `enable()` adds `body.deck`, calls `win_set_fullscreen(true)`, stores the previous fullscreen state, shows the footer hints. `disable()` reverses it. `handle("confirm")` clicks the focused element; `"back"` closes the modal or returns to the list; `"menu"` opens a small menu with `Quitter le mode Deck`; `"play"` triggers the focused game; `"favorite"` toggles it.

- [ ] **Step 4: Focus model**

`focusables()` selects visible, enabled `button, a[href], input, select, textarea, [tabindex]` inside `#shell` and `#modal`, excluding `[hidden]` and zero-size nodes. `move(direction)` chooses the nearest candidate whose center lies in the direction, weighted by axis distance and overlap; `scrollIntoView({ block: "nearest" })`. Re-apply focus after every render by calling `QuarkDeck.refocus()` from `renderAll()`, `renderSheet()`, and modal opening.

- [ ] **Step 5: Keyboard fallback**

When `body.deck` is active, arrows move, Enter confirms, Escape backs out, `Home` opens the menu. Do not intercept keys while an input/textarea is focused.

- [ ] **Step 6: Wire events and startup**

Load `deck.js` before `app.js`, subscribe to `quark://gamepad` in `boot()`, and call `QuarkDeck.init()` after the first render. Add the controller icon to the top bar when a gamepad was seen.

- [ ] **Step 7: Verify**

Run: `cd quark-tauri && cargo build`
Expected: success. Then run the demo with `--deck`, press keyboard arrows/Enter/Escape, and confirm focus moves and screens change.

- [ ] **Step 8: Commit**

**Interfaces:**

  - `InstallJob { cancel: Arc<AtomicBool>, progress: Arc<Mutex<InstallProgress>>, title: String, provider: String, product_id: String }`
  - command `provider_cancel(provider: String, product_id: String) -> Result<(), String>`
  - event `quark://provider-install-progress` with `{ key, provider, productId, state, percent, stage, speed, eta, written, total }`
  - UI state `app.transfers` keyed by `provider:productId`.

- [ ] **Step 1: Add the job registry**

Extend `AppState` with `installs: Mutex<HashMap<String, InstallJob>>`, initialize it in `main.rs`, and keep the job key `format!("{provider}:{product_id}")`.

- [ ] **Step 2: Emit progress and allow cancellation**

Create one `InstallProgress` and one `AtomicBool` per install. Pass them to every provider branch. Spawn a poller that emits the event every 400 ms while the install runs. `provider_cancel` sets the token and returns; the runner returns an error and the game becomes `Failed`. Refuse a fourth concurrent job with a clear error.

- [ ] **Step 3: Add the transfer UI**

`providers.js` subscribes to the progress event, stores entries in `app.transfers`, and renders a small panel from a download icon in `#top-right`. Each row shows title, stage, percentage or indeterminate bar, speed, ETA and `Annuler`. Remove finished rows after a short delay and refresh `providers_data`.

- [ ] **Step 4: Test cancellation**

Start a GOG/Epic install in demo or with a local fake command, call `provider_cancel`, and confirm the child process exits and the card shows the failed state. If no real store session is available, unit-test the job limits and the cancellation flag path.
